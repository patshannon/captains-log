# Captain's Log — 2026-05-25
Two workstreams today, both orbiting the same problem space: deployment orchestration and the state machines that drive it.

The heavier lift was on private-project-1, where a memory issue in the deployment monitor was quietly becoming a production concern. On large deployments with many tasks, the monitor was accumulating enough state to OOM — the fix was straightforward once the root cause was clear, but these are the bugs that remind you how easy it is to write something that looks fine at small scale and quietly grenades under real load. Alongside that, I tracked down a subtle logic error where failed-but-done tasks were being counted as active failures — a "ghost" flag that was causing the watchdog to report problems that weren't really there anymore. Small fix, but exactly the kind of thing that erodes trust in monitoring output over time.

The more interesting architectural work was unifying the promote and rollback operations into a single `publishDeployment` abstraction. These two actions were always two sides of the same coin — moving a deployment from one state to another — and treating them as separate codepaths was creating unnecessary divergence. Collapsing them reduces surface area and makes the state transitions easier to reason about. I also wired in Retry and Quick Refresh as discrete endpoints, which gives callers more control without baking polling logic into the client.

Private-project-2 got a parallel treatment on the frontend side. The Draft/Published model refactor is the UI expression of the same conceptual shift — making deployment state explicit and navigable rather than inferred. The in-panel Retry keeps the recovery flow close to where failures surface, and the stateless Quick Refresh avoids the stale-cache problems we'd been papering over. The failed-task counting fix here mirrors the backend fix in private-project-1, which tells me this was a shared misunderstanding of the task state model that had propagated across both layers.

Also dropped a CLAUDE.md into private-project-2 today. Increasingly convinced that writing down project context for AI-assisted development pays for itself quickly — it's essentially a forcing function to articulate the invariants and conventions you'd otherwise just carry in your head.
